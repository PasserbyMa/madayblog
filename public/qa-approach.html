QA Approach Document

버그를 어떻게 찾고, 판단하고, 보고하는가

QA 실무 경력은 없습니다. 대신 개발자로서 코드가 어디서 실패하는지를 직접 만들고 고치며 이해해왔습니다.
이 문서는 그 경험을 QA 관점으로 정리한 것입니다 — 실무에서 어떻게 일할 것인지에 대한 제 기준입니다.
원칙 01

경계값부터 확인한다

정상 케이스는 개발자도 이미 확인한 경우가 많습니다. 버그는 대부분 최대치, 최소치, 상태 전환점에서 나옵니다. 새 기능을 테스트할 때 가장 먼저 확인하는 것은 "이 기능이 한계 상황에서 어떻게 동작하는가"입니다.

개발자는 보통 중간값으로 구현하고 테스트합니다. 재화가 0일 때, 최대일 때, 딱 한 칸 모자랄 때 — 이 조건들이 실제 유저가 마주치는 구간이고, 코드가 예상치 못한 상태에 놓이는 구간입니다.

BUG-001
엘리프 무한 복제 — 왕사탕이 최대 보유량일 때만 발생하는 경계값 버그. 정상 보유량 상태에서는 재현되지 않습니다. 경계 조건을 먼저 확인하지 않았다면 발견하기 어려웠을 케이스입니다.

원칙 02

재현 가능해야 의미있다

재현 절차가 불분명한 버그 리포트는 개발팀에게 노이즈입니다. "가끔 발생하는 것 같아요"는 수정할 수 없습니다. 보고 전에 최소 조건을 특정하는 것이 먼저입니다.

기기 / OS / 앱 버전 — 어느 환경에서 발생하는가
선행 상태 — 어떤 상태에서 시작해야 재현되는가
재현율 — 100%인가, 간헐적인가
최소 재현 절차 — 불필요한 단계를 제거한 가장 짧은 경로

재현율이 낮은 버그는 "간헐적 발생 / 조건 특정 진행 중"으로 상태를 명시하고 열어둡니다. 섣불리 닫지 않습니다.

원칙 03

"왜"까지 담긴 리포트를 쓴다

"이렇게 됩니다"만 담긴 리포트와 "왜 이렇게 됐는지, 어디를 보면 되는지"까지 담긴 리포트는 다릅니다. 개발팀 입장에서 후자는 수정 시간을 단축합니다.

개발자 출신이라 서버 API 처리 방식, 이벤트 핸들러 구조, 상태 계산 로직을 추론할 수 있습니다. 그 추론을 리포트에 포함합니다 — 확정이 아닌 추정으로 명시하면서. 틀려도 괜찮습니다. 개발자가 방향을 잡는 데 도움이 되는 것이 목적입니다.

BUG-002
친밀도 스탯 5.5배 누적 — 리포트에 추정 원인을 포함했습니다.
newStat = prevStat + bonus[N] 대신 bonus[N] - bonus[N-1]을 더해야 한다는 delta/total 혼동 추론.

버그 심각도 판단 기준

Severity(기술적 심각도)와 Priority(비즈니스 우선순위)를 구분해서 판단합니다.

Priority 높음
Priority 낮음
Severity 높음
P1 · 즉시 수정 크리티컬 게임 경제 붕괴, 진행 불가, 악용 가능 버그. 즉시 공유하고 핫픽스 요청.
P2 · 계획 수정 높음 기술적으로 심각하지만 즉각 영향이 제한적. 다음 패치 일정에 포함.
Severity 낮음
P2 · 빠른 수정 중간 기술적 영향은 작지만 유저 노출이 높음. 이벤트 기간 비주얼 버그 등.
P3 · 백로그 낮음 영향 범위 좁고 우선순위 낮음. 기록하고 추후 처리.
예시: UI 텍스트 오탈자는 Severity가 낮습니다. 하지만 신규 캐릭터 출시 당일이라면 Priority는 높아집니다 — 같은 버그도 타이밍에 따라 우선순위가 달라집니다.
