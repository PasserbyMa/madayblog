CHAPTER 1-1
IP와 Port

IP — 인터넷에서의 주소

현실에서 택배를 보내려면 주소가 필요하듯, 인터넷에서 데이터를 보내려면 IP 주소가 필요하다.

현실:    서울시 강남구 역삼동 123번지
인터넷:  129.154.xx.xx  ← 서버 주소

IP는 두 종류가 있다.

종류설명예시
공인 IP인터넷에서 식별되는 주소. 전 세계 유일OCI 서버 IP
사설 IP내부 네트워크에서만 사용. 외부 접근 불가172.x.x.x (Docker 내부)

Port — 건물 안의 호실

IP가 건물 주소라면, Port는 호실 번호다. 서버는 여러 서비스를 동시에 띄울 수 있고, Port로 구분한다.

서버IP:80    → 80호실  (HTTP)
서버IP:443   → 443호실 (HTTPS)
서버IP:27017 → 27017호실 (MongoDB)
서버IP:9092  → 9092호실 (Kafka)

docker-compose의 ports 설정

ports:
  - "443:443"   # 외부 443 → 컨테이너 내부 443
  - "80:80"     # 외부 80  → 컨테이너 내부 80

외부포트:내부포트 형식이다. MongoDB에 ports 설정이 없는 건 의도적인 보안 설계 — 외부에서 직접 접근할 수 없게 막아둔 것이다.

// 정리
IP = 서버 주소 (어디로 갈 건지) Port = 서비스 번호 (거기서 누구한테 전달할 건지) 공인 IP = 인터넷에서 보이는 주소 사설 IP = 내부에서만 쓰는 주소 ports: "443:443" = 외부:내부 포트 매핑
CHAPTER 1-2
HTTP 요청이 블로그까지 도달하는 과정

HTTP가 뭔가

인터넷에서 데이터를 주고받는 규칙(프로토콜)이다. 브라우저와 서버가 대화할 때 형식을 맞춰야 서로 이해할 수 있고, 그 형식이 HTTP다.

브라우저: "GET /api/posts 주세요"   ← 요청 (Request)
서버:     "200 OK, 여기 데이터요"   ← 응답 (Response)

요청의 구조

GET /api/posts HTTP/1.1
Host: madayblog.com
Authorization: Bearer eyJhbGci...
Content-Type: application/json
구성요소설명예시
Method뭘 할 건지GET, POST, PUT, DELETE
Path어디서 할 건지/api/posts
Headers부가 정보인증, 콘텐츠 타입 등

HTTP Method

Method의미사용 예
GET데이터 가져와글 목록 조회
POST데이터 만들어글 등록
PUT/PATCH데이터 수정해글 수정
DELETE데이터 지워글 삭제

요청이 블로그까지 가는 전체 흐름

브라우저가 "https://madayblog.com/api/posts" 요청
       │
① DNS 조회 → "madayblog.com이 어느 IP야?" → 서버IP 반환
       │
② 서버IP:443 으로 TCP 연결 (HTTPS라 443)
       │
③ Nginx가 받음 → "이 요청 어디로 보내지?"
       │
④ /api/* → Next.js:8080 으로 전달
       │
⑤ Next.js가 처리 → MongoDB 조회
       │
⑥ 응답 역순으로 반환: Next.js → Nginx → 브라우저

HTTP vs HTTPS

HTTPHTTPS
데이터평문 전송 (중간에 읽힘)암호화 전송 (읽을 수 없음)
포트80443
인증서불필요SSL 인증서 필요 (Certbot)

응답 상태 코드

코드의미언제

201생성됨POST 성공

403권한 없음관리자 아님
404못 찾음없는 경로
500서버 에러서버 코드 오류
// 정리
HTTP = 브라우저와 서버가 대화하는 규칙 HTTPS = HTTP + 암호화 (Certbot이 인증서 관리) 요청 = Method(뭘) + Path(어디서) + Headers(부가정보) 응답 = 상태코드 + 데이터 흐름: 브라우저 → DNS → Nginx → Next.js → MongoDB ← 역순으로 응답
CHAPTER 1-3
DNS가 뭔가

전화번호부

사람은 "naver.com"으로 기억하지만, 컴퓨터는 IP 주소로만 통신한다. DNS는 도메인 → IP 주소로 변환해주는 전화번호부다.

사람이 입력:  naver.com
DNS가 변환:  223.130.200.107
컴퓨터가 접속: 223.130.200.107:443

변환 과정

① 브라우저 캐시 확인 → 있으면 바로 접속
② OS 캐시 확인
③ DNS 서버에 질문 → "naver.com IP가 뭐야?" → IP 반환
④ 그 IP로 접속

이 과정이 수십 밀리초 안에 끝나서 체감하지 못한다.

DNS 레코드 종류

레코드역할예시
A도메인 → IPv4 주소madayblog.com → 서버IP
CNAME도메인 → 다른 도메인www.example.com → example.com
MX이메일 서버 주소메일 받을 서버 지정
TXT텍스트 정보도메인 소유 인증

TTL — 캐시 유효 시간

DNS 응답에는 TTL(Time To Live)이 붙는다. "이 정보는 N초 동안 믿어도 돼"라는 의미다.

IP를 바꿨는데 왜 아직 구 서버로 접속되지?
→ TTL이 아직 안 지났기 때문
→ TTL 시간만큼 기다려야 전파 완료 (최대 48시간)

Certbot과 DNS의 연결

Certbot이 SSL 인증서 발급받을 때 Let's Encrypt가 "이 서버 진짜 주인 맞아?"를 확인한다. HTTP 방식은 /.well-known/acme-challenge/ 경로에 파일을 올려서 증명한다. nginx.conf에 해당 경로 설정이 있는 이유가 이것이다.

// 정리
DNS = 도메인을 IP로 변환하는 전화번호부 A 레코드 = 도메인 → IP 매핑 (블로그에서 쓰는 것) TTL = DNS 캐시 유효 시간 (IP 바꾸면 이 시간만큼 전파 지연) 흐름: 도메인 입력 → DNS 조회 → IP 획득 → 서버 접속

Forward Proxy vs Reverse Proxy

Forward ProxyReverse Proxy
누구를 위한 것클라이언트서버
숨기는 것클라이언트 IP서버 내부 구조
실제 사용VPN, 사내망Nginx, 로드밸런서
Q. Forward와 Reverse가 그림이 똑같아 보이는데 뭐가 달라?
A. 누구를 위한 프록시냐가 다르다. Forward는 내가 인터넷에 접속할 때 내가 누군지 숨겨주고, Reverse는 내가 접속하려는 서버가 어떤지를 숨겨준다.
// 정리
Nginx = 문지기 (Reverse Proxy) 역할: ① HTTPS 처리 (SSL 인증서 관리) ② 요청을 내부 서버로 전달 ③ 내부 구조 숨김 (보안) ④ 여러 서비스를 하나의 도메인으로 연결
CHAPTER 2-2
Reverse Proxy 동작 원리

요청이 Nginx를 거치는 과정

① 사용자가 https://madayblog.com/api/posts 요청
② Nginx가 받음 → 설정 파일 확인
③ /api/ 경로 → Next.js:8080 으로 전달
④ Next.js 처리 → MongoDB 조회 → 응답 생성
⑤ Next.js → Nginx → 사용자

사용자는 Nginx하고만 대화. Next.js가 있는지도 모름.

Nginx가 요청 전달 시 추가하는 헤더

X-Real-IP: 123.456.789.0        ← 진짜 사용자 IP
X-Forwarded-For: 123.456.789.0  ← 거쳐온 IP 목록
X-Forwarded-Proto: https        ← 원래 프로토콜
Host: madayblog.com             ← 원래 도메인

nginx.conf에 proxy_set_header X-Real-IP $remote_addr;가 있는 이유다. Next.js가 진짜 사용자 IP를 알 수 있게 해준다.

upstream — 내부 서버 묶음

upstream nextjs_upstream {
    server mablog_nextjs:8080;
}

# 여러 서버로 묶으면 로드밸런싱
upstream nextjs_upstream {
    server nextjs_1:8080;
    server nextjs_2:8080;
    server nextjs_3:8080;
}

로드밸런싱 알고리즘

방식동작설정언제
Round Robin순서대로 (기본값)별도 설정 없음일반적인 경우
Least Conn연결 적은 서버로least_conn;요청 무게 들쑥날쑥
IP Hash같은 IP → 같은 서버ip_hash;세션 유지 필요 (옛날 방식)
Q. IP Hash가 제일 무난한가?
A. 아니다. 요즘은 세션을 Redis 같은 별도 저장소에 두기 때문에 어느 서버로 가도 세션이 공유된다. Round Robin으로 충분한 경우가 대부분이다. IP Hash는 옛날 방식.

location — 경로별 분기

location /api/ {
    proxy_pass http://nextjs_upstream;
}

location /stats/ {
    proxy_pass http://springboot:8080;  # 나중에 추가
}

location / {
    proxy_pass http://nextjs_upstream;
}
// 정리
Nginx의 핵심 역할: ① location으로 경로 보고 판단 ② proxy_pass로 내부 서버에 전달 ③ 헤더 추가해서 사용자 정보 전달 ④ upstream으로 여러 서버 묶어서 부하 분산

upstream

아래에서 proxy_pass http://nextjs_upstream으로 참조한다.

HTTP 서버 (80 포트)

server {
    listen 80;
    server_name madayblog.com www.madayblog.com;

    # Certbot 인증서 갱신용
    location ^~ /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    # 나머지 전부 HTTPS로 강제 이동
    location / {
        return 301 https://$host$request_uri;
    }
}

301은 "영구 이동" 상태 코드다. 브라우저가 받으면 자동으로 https로 다시 요청한다.

HTTPS 서버 (443 포트)

listen 443 ssl http2;

ssl_certificate /etc/letsencrypt/live/madayblog.com/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/madayblog.com/privkey.pem;

ssl_protocols TLSv1.2 TLSv1.3;  # 오래된 버전 차단

Proxy 설정 핵심

proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";

이 세 줄이 WebSocket / SSE 지원을 위한 설정이다. Docker 컨테이너 상태를 실시간 스트림(SSE)으로 받아오는 기능이 이것 때문에 동작한다.

전체 흐름

사용자 → http://madayblog.com
            │
         80 포트 → 301 리다이렉트
            │
         https://madayblog.com
            │
         443 포트 → SSL 복호화
            │
         location / 매칭
            │
         proxy_pass → mablog_nextjs:8080
            │
         Next.js 처리 → 응답
// 정리
80 포트 = HTTP 접속 → HTTPS로 강제 리다이렉트 (301) 443 포트 = HTTPS 처리 → Next.js로 전달 Upgrade/Connection 헤더 = WebSocket/SSE 지원 ssl_protocols TLSv1.2/1.3 = 오래된 TLS 차단 (보안) 로그 두 곳 저장 = Docker stdout + 파이프라인 파일
CHAPTER 3-1
컨테이너가 VM이랑 뭐가 다른가

VM — 컴퓨터 안에 컴퓨터

물리 서버
└── Hypervisor
    ├── VM 1: OS + 라이브러리 + 앱  (수 GB)
    ├── VM 2: OS + 라이브러리 + 앱  (수 GB)
    └── VM 3: OS + 라이브러리 + 앱  (수 GB)

OS를 통째로 올리니까 시작에 수 분 걸리고, VM 하나당 수 GB를 차지한다.

Container — 프로세스 격리

물리 서버
└── OS (Linux) ← 하나, 공유
    └── Docker Engine

트랜잭션이 보장해야 하는 4가지 성질이다.

속성의미예시
Atomicity (원자성)전부 성공 또는 전부 실패송금 중 에러 → 전부 취소
Consistency (일관성)데이터가 항상 유효한 상태잔액이 음수가 되면 안 됨
Isolation (격리성)동시 작업이 서로 영향 안 줌두 사람이 동시에 같은 좌석 예매 불가
Durability (지속성)성공한 작업은 영구 보존서버 꺼져도 데이터 유지

MongoDB vs RDB 트랜잭션

RDB (PostgreSQL 등):
BEGIN;
  UPDATE accounts SET balance = balance - 100000 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100000 WHERE id = 2;
COMMIT;  -- 성공 시 확정
-- 에러 나면 자동 ROLLBACK

MongoDB:
단일 문서 내 작업은 원자적으로 처리됨
여러 문서 걸친 트랜잭션은 별도 설정 필요 (버전 4.0+)

내 블로그에서 트랜잭션이 필요한가

현재는 필요 없다. 포스트 하나를 저장하거나 삭제하는 단순 작업이라 여러 컬렉션에 걸친 복잡한 트랜잭션이 없다.

나중에 Spring Boot + PostgreSQL로 방문자 통계를 관리하게 되면, 여러 테이블에 동시에 써야 하는 상황이 생겨서 트랜잭션이 중요해진다.

// 정리
트랜잭션 = 여러 작업을 하나로 묶음 (전부 성공 or 전부 실패) ACID = 트랜잭션이 보장해야 하는 4가지 성질 RDB = 트랜잭션 지원 강력 MongoDB = 단일 문서는 원자적, 다중 문서 트랜잭션은 제한적
CHAPTER 5-1
Kafka — 메시지 큐가 왜 필요한가

메시지 큐 없이 직접 연결하면

Nginx → Logstash → Elasticsearch

문제:
① Elasticsearch가 다운되면? 로그 유실
② 트래픽이 폭발하면? Logstash가 버티지 못함
③ 나중에 다른 곳에도 로그를 보내고 싶으면?
   → Nginx 설정을 다 바꿔야 함

Kafka를 중간에 넣으면

Nginx → Logstash → [Kafka] → Elasticsearch
                              → 다른 시스템 (나중에 추가)

이점:
① Elasticsearch가 다운돼도 Kafka가 메시지 보관
② 트래픽이 폭발해도 Kafka가 버퍼 역할
③ 새 시스템 추가가 Kafka 구독만 하면 됨

실생활 비유

Kafka = 택배 허브 센터

보내는 사람 (Producer): "이 짐 맡아줘"
허브 센터 (Kafka):       보관하다가 순서대로 처리
받는 사람 (Consumer):    "내 거 꺼내갈게"

핵심: 보내는 사람과 받는 사람이 동시에 연결될 필요 없음
      → 느슨한 연결 (Decoupling)

내 파이프라인에서

Producer: Logstash (nginx 로그를 Kafka에 전송)
Topic:    nginx-logs (메시지가 저장되는 공간)
Consumer: Logstash 두 번째 파이프라인 (Kafka에서 꺼내 Elasticsearch에 저장)
// 정리
메시지 큐 = 생산자와 소비자를 느슨하게 연결하는 중간 버퍼 이점: ① 장애 격리 — 한쪽 다운돼도 메시지 보관 ② 부하 분산 — 트래픽 폭발 시 버퍼 역할 ③ 확장성 — 새 소비자 추가가 쉬움
CHAPTER 5-2
Topic, Offset, Consumer Group

Topic — 메시지 분류함

Kafka 안에 여러 Topic이 있을 수 있음

nginx-logs   ← nginx 접속 로그
app-errors   ← 앱 에러 로그
user-events  ← 사용자 행동 로그

Producer는 특정 Topic에 메시지를 보내고
Consumer는 특정 Topic을 구독해서 읽음

Offset — 메시지 위치 번호

Kafka의 메시지는 Topic 안에 순서대로 쌓인다. 각 메시지는 Offset이라는 번호를 가진다.

Topic: nginx-logs
┌────────┬────────┬────────┬────────┬────────┐
│offset 0│offset 1│offset 2│offset 3│offset 4│
│ 로그A  │ 로그B  │ 로그C  │ 로그D  │ 로그E  │
└────────┴────────┴────────┴────────┴────────┘

Consumer가 offset 2까지 읽었다면
→ 다음에 offset 3부터 이어서 읽음
→ 서버가 재시작돼도 어디까지 읽었는지 기억

이게 Kafka와 일반 메시지 큐의 가장 큰 차이다. 메시지를 읽어도 삭제되지 않아서, 나중에 다시 읽거나 다른 Consumer가 처음부터 읽을 수 있다.

Consumer Group

같은 Group의 Consumer들은 메시지를 나눠서 처리
다른 Group의 Consumer들은 같은 메시지를 각자 처리

Group A (로그 저장팀): offset 0~4 전부 처리
Group B (알림팀):     offset 0~4 전부 처리 (독립적으로)

→ 같은 메시지를 여러 용도로 사용 가능
// 정리
Topic = 메시지 분류함 (채널) Offset = 메시지 위치 번호 (어디까지 읽었는지 기억) Consumer Group = 독립적인 소비자 집합 Kafka의 특징: 읽어도 메시지 삭제 안 됨 → 여러 Consumer가 독립적으로 처리 가능

핵심 원칙

1. URL은 자원(Resource)을 표현한다

PATCH  /api/posts/my-slug  → 일부 수정
DELETE /api/posts/my-slug  → 삭제

3. 상태 코드를 올바르게 사용한다

200 OK          → 조회 성공
201 Created     → 생성 성공
400 Bad Request → 요청 데이터 오류
401 Unauthorized → 인증 필요
403 Forbidden   → 권한 없음
404 Not Found   → 리소스 없음
500 Server Error → 서버 오류

CHAPTER 6-2
인증 — JWT vs Session

Session 방식 (전통적)

① 사용자 로그인
② 서버가 세션 생성 → 메모리/DB에 저장
③ 세션 ID를 쿠키로 전달
④ 이후 요청마다 쿠키의 세션 ID 확인
⑤ 서버가 세션 저장소에서 조회 → 인증 확인

문제: 서버가 여러 대면 세션 공유가 필요 (Redis 등)
     서버에 상태가 생김 (Stateful)

JWT 방식 (현대적)

① 사용자 로그인
② 서버가 JWT 토큰 생성 → 클라이언트에 전달
③ 이후 요청마다 토큰을 헤더에 포함
   Authorization: Bearer eyJhbGci...
④ 서버가 토큰 서명 검증 → 인증 확인
   (DB 조회 없이 서명만으로 확인 가능)

장점: 서버에 상태 없음 (Stateless)
      서버 여러 대여도 문제없음

JWT 구조

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjM0In0.abc123

헤더.페이로드.서명
 │       │       └── 위변조 방지 서명
 │       └────────── 실제 데이터 (userId, role 등)
 └────────────────── 알고리즘 정보

내 블로그 인증 구조

GitHub OAuth → NextAuth.js → JWT

① GitHub 로그인 버튼 클릭
② GitHub 인증 페이지로 이동
③ 인증 완료 → NextAuth가 JWT 생성
④ JWT에 GitHub userId 포함
⑤ API 요청 시 userId를 환경변수의 ADMIN_ID와 비교
   → 같으면 관리자 권한 부여
// 정리
Session = 서버에 상태 저장 (Stateful) 서버 여러 대면 공유 필요 (Redis) JWT = 서버에 상태 없음 (Stateless) 토큰 서명으로 검증, DB 조회 불필요 Authorization: Bearer {token} 형식 내 블로그: GitHub OAuth + NextAuth + JWT

비동기 심화 — Promise.all과 AbortSignal

비동기가 뭔지 다시 정리

자바스크립트는 한 번에 한 가지 일만 한다. 근데 네트워크 요청처럼 기다려야 하는 일을 동기로 처리하면 그 동안 아무것도 못 한다.

비동기(async/await)를 쓰면 기다리는 동안 다른 일을 할 수 있다.

// 동기 방식 — 순서대로 기다림
const a = fetchArticle('인벤 글1')   // 3초 대기
const b = fetchArticle('인벤 글2')   // 또 3초 대기
// 총 6초

// 비동기 + Promise.all — 동시에 실행
const [a, b] = await Promise.all([
    fetchArticle('인벤 글1'),
    fetchArticle('인벤 글2'),
])
// 총 3초 (가장 오래 걸리는 것만큼만)

Promise.all

여러 개의 비동기 작업을 동시에 실행하고, 전부 완료될 때까지 기다린다.

// 실제 사용 예 — 5개 글 본문을 병렬 크롤링
await Promise.all(items.map(async (item) => {
    item.text = await fetchArticleText(item.url)
}))

// map → [Promise, Promise, Promise, Promise, Promise]
// Promise.all → 동시에 실행, 전부 완료 대기
Promise.all순차 await
실행 방식동시 (병렬)하나씩 (순차)
소요 시간가장 느린 것만큼전부 합산
실패 시하나라도 실패하면 전체 실패실패한 것에서 멈춤
적합한 상황독립적인 여러 요청순서가 중요한 작업

Promise.allSettled — 실패해도 계속

크롤링처럼 일부가 실패해도 나머지는 계속 돌아야 할 때 쓴다.

const results = await Promise.allSettled([
    crawlInven(query),
    crawlDcinside(query),
    crawlNaver(query),
])

results.forEach(r => {
    if (r.status === 'fulfilled') console.log(r.value)
    if (r.status === 'rejected')  console.log('실패:', r.reason)
})

AbortSignal — 요청 타임아웃

느린 서버에 요청을 보냈을 때 무한정 기다리지 않도록 시간 제한을 건다.

// 5초 안에 안 오면 에러 던짐
const res = await fetch(url, {
    signal: AbortSignal.timeout(5000),
})

// 직접 컨트롤하고 싶을 때
const controller = new AbortController()
setTimeout(() => controller.abort(), 5000)

const res = await fetch(url, {
    signal: controller.signal,
})
// 정리
Promise.all = 여러 요청 병렬 실행 → 전부 성공해야 완료 Promise.allSettled = 실패해도 나머지 계속 → 결과 개별 확인 AbortSignal.timeout = fetch에 타임아웃 설정 → 무한 대기 방지 크롤링처럼 외부 요청이 많을수록 Promise.all이 필수다.

MongoDB 집계 쿼리 — aggregate 파이프라인

aggregate란

find()는 문서를 그대로 가져온다. aggregate()는 데이터를 변환·집계할 수 있다. SQL의 GROUP BY, COUNT, SUM을 MongoDB에서 담당한다.

// SQL
SELECT path, COUNT(*) as count
FROM visitor_stats
WHERE timestamp >= today
GROUP BY path
ORDER BY count DESC
LIMIT 5;

// MongoDB aggregate
collection.aggregate([
    { $match:  { timestamp: { $gte: todayStart } } },  // WHERE
    { $group:  { _id: '$path', count: { $sum: 1 } } }, // GROUP BY + COUNT
    { $sort:   { count: -1 } },                        // ORDER BY
    { $limit:  5 },                                    // LIMIT
])

파이프라인 단계 (stage)

aggregate는 여러 단계(stage)를 순서대로 실행한다. 앞 단계의 결과가 다음 단계의 입력이 된다.

Stage역할SQL 대응
$match조건으로 필터WHERE
$group필드 기준으로 묶기GROUP BY
$sort정렬ORDER BY
$limit개수 제한LIMIT
$project반환할 필드 선택SELECT 컬럼 지정
$addFields새 필드 추가/계산computed column

실제 예제 — 오늘 방문자 수

const todayStart = new Date();
todayStart.setHours(0, 0, 0, 0);  // 오늘 00:00

const result = await collection.aggregate([
    // 1단계: 오늘 데이터 + 정적 파일 제외
    { $match: { timestamp: { $gte: todayStart }, is_static: false } },

    // 2단계: 전체를 하나로 묶어서 집계
    {
        $group: {
            _id: null,                           // 전체를 하나의 그룹으로
            total: { $sum: 1 },                  // 총 요청 수
            unique_ips: { $addToSet: '$client_ip' }  // 중복 없는 IP 집합
        }
    },

    // 3단계: unique IP 개수 계산
    { $project: { total: 1, unique_count: { $size: '$unique_ips' } } },
]).toArray();

CHAPTER 10-4
TTL 인덱스 — 데이터 자동 만료

TTL 인덱스란

TTL(Time To Live) 인덱스는 MongoDB가 일정 시간이 지난 문서를 자동으로 삭제하는 기능이다. 로그처럼 오래된 데이터가 필요 없을 때 직접 삭제 쿼리를 짜지 않아도 된다.

생성 방법

// Python (pymongo)
collection.create_index(
    [("timestamp", ASCENDING)],
    expireAfterSeconds=30 * 24 * 3600,  # 30일 = 2,592,000초
    name="ttl_30days",
)

// JavaScript (mongoose / mongosh)
db.visitor_stats.createIndex(
    { timestamp: 1 },
    { expireAfterSeconds: 2592000, name: "ttl_30days" }
)

MongoDB는 백그라운드에서 약 60초마다 만료된 문서를 검사하고 삭제한다. 정확히 만료 시각에 삭제되지는 않지만 60초 이내에 처리된다.

주의 — 같은 키에 인덱스 중복 불가

MongoDB는 동일한 키에 두 인덱스를 만들 수 없다. TTL 인덱스를 만들기 전에 같은 키의 일반 인덱스가 있으면 충돌한다.

# 오류 메시지
OperationFailure: An equivalent index already exists with a different name and options.
Requested index: { key: { timestamp: 1 }, name: "ttl_30days", expireAfterSeconds: 2592000 }
existing index: { key: { timestamp: 1 }, name: "timestamp_1" }

# 해결: 기존 인덱스 삭제 후 TTL로 재생성
try:
    collection.drop_index("timestamp_1")
except Exception:
    pass  # 없으면 무시
collection.create_index(
    [("timestamp", ASCENDING)],
    expireAfterSeconds=30 * 24 * 3600,
    name="ttl_30days",
)

용량 계산 — 얼마나 쌓이나

visitor_stats는 30일치만 보관하므로 최대 용량을 미리 계산할 수 있다.

일 평균 적재: ~2,900건
문서 1건 크기: ~0.32 KB
30일 최대: 2,900 × 30 = 87,000건
최대 용량: 87,000 × 0.32 KB ≈ 27 MB

서버 디스크 116 GB 기준으로 0.02%도 안 되는 수준이다. 부담 없다.

TTL vs 수동 삭제 vs Capped Collection

방법특징적합한 상황
TTL 인덱스날짜 기준 자동 만료로그, 세션, 캐시
수동 deleteMany조건을 직접 제어복잡한 조건으로 삭제
Capped Collection최대 크기/건수 초과 시 오래된 것 자동 삭제실시간 로그 테일링

visitor_stats처럼 "30일보다 오래된 것 지워라"는 조건은 TTL 인덱스가 가장 깔끔하다.

// 정리
TTL 인덱스 = MongoDB가 오래된 문서를 자동 삭제해주는 기능 expireAfterSeconds: 초 단위 (30일 = 2,592,000) 삭제는 약 60초 간격으로 백그라운드에서 실행됨 같은 키에 일반 인덱스가 있으면 TTL로 만들 수 없음 → drop 후 재생성 visitor_stats 30일 최대 용량: 약 27 MB → 소형 서버도 부담 없음

CHAPTER 12-1
로드밸런싱이 뭔가 — 개념과 필요성

문제 상황

서버 한 대로 서비스를 운영하다 보면 한계가 온다.

사용자 1 ─┐
사용자 2 ─┤──▶ 서버 1대 ← CPU 100%, 메모리 부족, 응답 느림
사용자 3 ─┘

해결책은 두 가지다.

방법설명한계
Scale Up (수직 확장)서버 사양을 올린다 (CPU, RAM 증가)비용이 기하급수적으로 증가, 한계가 있음
Scale Out (수평 확장)서버를 여러 대로 늘린다여러 서버에 트래픽을 나눠야 함 → 로드밸런서 필요

로드밸런서의 역할

사용자 1 ─┐
사용자 2 ─┤──▶ [로드밸런서] ──▶ 서버 A
사용자 3 ─┘          │──────▶ 서버 B
                      └──────▶ 서버 C

로드밸런서는 들어오는 요청을 여러 서버에 분산시킨다. 사용자는 로드밸런서의 IP 하나만 알면 되고, 뒤에 서버가 몇 대인지 몰라도 된다.

분산 알고리즘 종류

알고리즘방식특징
Round RobinA → B → C → A → B → C...기본값. 순서대로 돌아가며 배분
Least Connections현재 연결 수가 가장 적은 서버로서버별 처리 속도가 다를 때 유리
IP Hash사용자 IP를 해싱해서 항상 같은 서버로로그인 세션 유지에 필요 (Sticky Session)
Weight가중치 높은 서버에 더 많이 배분서버 사양이 다를 때

L4 vs L7 로드밸런싱

L4 (Transport Layer)L7 (Application Layer)
기준IP + PortURL, 헤더, 쿠키 등
속도빠름 (내용 안 봄)상대적으로 느림
기능단순 분산경로별 분산, 컨텐츠 기반 라우팅
예시AWS NLBNginx, AWS ALB
# L7 예시: URL 경로에 따라 다른 서버로
/api/*    → API 서버들
/static/* → 정적 파일 서버
/         → Next.js 서버들
// 정리
로드밸런싱 = 트래픽을 여러 서버에 나누는 것 Scale Up = 서버 사양 증가 (한계 있음) Scale Out = 서버 대수 증가 → 로드밸런서 필요 Round Robin = 순서대로 (기본) IP Hash = 같은 사용자는 항상 같은 서버 (세션 유지) Least Conn = 현재 가장 한가한 서버로 L4 = IP/Port 기준 빠른 분산 L7 = URL/헤더 기준 스마트한 분산 (Nginx가 여기)
CHAPTER 12-2
Nginx로 로드밸런싱 적용하기 — 단계별

지금 내 구조 (단일 서버)

사용자 ──▶ Nginx ──▶ Next.js 1대

트래픽이 많아지면 Next.js 컨테이너 하나로 버티기 힘들다. 같은 서버 안에서도 컨테이너를 여러 개 띄워서 로드밸런싱할 수 있다.

STEP 1 — Next.js 컨테이너 여러 개 띄우기

# docker-compose.yml
services:
    nextjs_1:
        build: .
        container_name: mablog_nextjs_1
        expose:
            - "8080"
        networks:
            - mablog_network

    nextjs_2:
        build: .
        container_name: mablog_nextjs_2
        expose:
            - "8080"
        networks:
            - mablog_network

포트를 외부에 열 필요 없다. Nginx가 내부 네트워크에서 직접 접근한다.

STEP 2 — Nginx upstream 설정

# nginx.conf
http {
    # 로드밸런싱 대상 서버 그룹 정의
    upstream nextjs_servers {
        # 기본: Round Robin (순서대로)
        server mablog_nextjs_1:8080;
        server mablog_nextjs_2:8080;

        # 가중치 적용 (nextjs_1이 2배 더 받음)
        # server mablog_nextjs_1:8080 weight=2;
        # server mablog_nextjs_2:8080 weight=1;

        # 최소 연결 수 방식
        # least_conn;

        # IP Hash (세션 유지)
        # ip_hash;
    }

    server {
        listen 443 ssl;

        location / {
            proxy_pass http://nextjs_servers;  # upstream 이름 지정
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }
    }
}

STEP 3 — 헬스체크 추가 (장애 자동 제외)

upstream nextjs_servers {
    server mablog_nextjs_1:8080 max_fails=3 fail_timeout=30s;
    server mablog_nextjs_2:8080 max_fails=3 fail_timeout=30s;
    # max_fails=3   : 3번 실패하면 다운 판정
    # fail_timeout  : 30초 동안 요청 안 보냄 → 이후 다시 시도
}

서버 하나가 죽어도 Nginx가 자동으로 감지하고 나머지 서버로만 요청을 보낸다.

STEP 4 — docker-compose scale 명령어

# 명령어 하나로 컨테이너 개수 조절
docker-compose up -d --scale mablog_nextjs=3

# 이러면 mablog_nextjs 컨테이너가 3개 자동 생성됨
# mablog_nextjs_1, mablog_nextjs_2, mablog_nextjs_3

scale을 쓰려면 nginx.conf에서 컨테이너 이름 대신 서비스 이름으로 지정해야 한다. Docker가 같은 네트워크 안에서 자동으로 라운드로빈 DNS를 제공한다.

upstream nextjs_servers {
    server mablog_nextjs:8080;  # 서비스 이름 하나만 써도 됨
    # Docker가 mablog_nextjs_1, 2, 3 으로 알아서 분산
}
// 적용 순서 정리
1. docker-compose.yml에 같은 앱 컨테이너 여러 개 정의 2. nginx.conf에 upstream 블록으로 서버 그룹 정의 3. proxy_pass에 upstream 이름 지정 4. max_fails / fail_timeout으로 장애 서버 자동 제외 5. --scale 명령어로 컨테이너 수 동적 조절 지금 내 서버는 트래픽이 적어서 필요 없지만 면접에서 "Scale Out 어떻게 하나요?" 물으면 이 흐름대로 답할 수 있다.

무중단 배포 (Zero Downtime Deploy)

새 버전 배포 시 서비스를 잠깐도 끊지 않는 방법이다.

# 일반 배포 (중단 있음)
docker-compose down       # ← 여기서 서비스 중단
docker-compose up --build # ← 빌드 완료까지 다운타임

# 무중단 배포 순서
1. 새 버전 이미지 빌드 (기존 컨테이너는 계속 서비스 중)
   docker-compose build mablog_nextjs

2. 새 컨테이너 하나 추가로 띄우기
   docker-compose up -d --scale mablog_nextjs=2 --no-recreate

3. Nginx가 자동으로 새 컨테이너 포함해서 분산
   (헬스체크 통과하면 트래픽 들어옴)

4. 구버전 컨테이너 제거
   docker-compose up -d --scale mablog_nextjs=1

Blue-Green 배포

가장 안전한 무중단 배포 방식이다.

현재 상태: Blue(구버전) 서비스 중
                    사용자 ──▶ Nginx ──▶ [Blue]

1단계: Green(신버전) 준비
                    사용자 ──▶ Nginx ──▶ [Blue]
                                          [Green] ← 준비 중

2단계: Nginx 설정 변경 (nginx -s reload, 무중단)
                    사용자 ──▶ Nginx ──▶ [Green]
                               [Blue] ← 대기 (문제 생기면 즉시 롤백)

3단계: Blue 제거
                    사용자 ──▶ Nginx ──▶ [Green]

문제가 생기면 Nginx 설정만 다시 바꾸면 구버전으로 즉시 롤백이 가능하다. 이게 Blue-Green의 핵심이다.

Nginx 설정 무중단 반영

# nginx.conf 수정 후 문법 검사
docker exec mablog_proxy nginx -t

# 검사 통과하면 무중단으로 설정 반영 (서비스 중단 없음)
docker exec mablog_proxy nginx -s reload

nginx -s reload는 기존 연결은 유지하면서 새 설정을 반영한다. restart와 달리 중단이 없다.

// 정리
헬스체크 = 서버 생존 여부 주기적 확인 → 죽은 서버는 로드밸런서가 자동 제외 무중단 배포 = 서비스 중단 없이 새 버전 배포 순서: 새 컨테이너 추가 → 트래픽 전환 → 구버전 제거 Blue-Green = 구버전/신버전 동시 유지 → 문제 생기면 Nginx 설정만 바꿔서 즉시 롤백 nginx -s reload = 설정 반영 (무중단) nginx -t = 설정 문법 검사 (반영 전 필수)
