2. Spring / Spring Boot 기초

DI (Dependency Injection) — 의존성 주입

// DI 없이 — 직접 생성 → 강한 결합
class OrderService {
    private PayService payService = new PayService();
}

// DI 사용 — Spring이 주입 → 느슨한 결합
@Service
class OrderService {
    private final PayService payService;

    @Autowired  // 또는 생성자 주입 (권장)
    public OrderService(PayService payService) {
        this.payService = payService;
    }
}
면접 답변
"객체를 직접 생성하지 않고 외부(Spring 컨테이너)에서 주입받는 방식입니다. 결합도를 낮춰 테스트와 유지보수가 쉬워집니다."

IoC (Inversion of Control) — 제어의 역전

객체 생성과 관리를 개발자가 아닌 Spring 컨테이너가 담당. DI가 IoC를 구현하는 방법 중 하나.

3. Spring 심화 (실무 어노테이션)

@Bean / @Configuration 동작 원리

@Configuration          // 이 클래스를 Spring 설정 파일로 등록
public class AppConfig {

    @Bean               // 반환 객체를 Spring 컨테이너에 Bean으로 등록
    public DataSource dataSource() {
        return DataSourceBuilder.create().build();
    }
}
  • @Configuration — 내부 @Bean 메서드를 CGLIB 프록시로 감싸서, 같은 @Bean을 여러 번 호출해도 싱글톤 보장
  • @Bean — 메서드 이름이 Bean 이름이 됨 (dataSource → "dataSource")
  • Spring 컨테이너 = ApplicationContext. 앱 시작 시 @Bean 메서드를 모두 실행해서 객체를 미리 만들어둠

@ConfigurationProperties — 프로퍼티 자동 바인딩

# application.properties
maria.datasource.jdbc-url=jdbc:mariadb://localhost:3306/practicedb
maria.datasource.username=mariauser
maria.datasource.password=Maria1234!
maria.datasource.driver-class-name=org.mariadb.jdbc.Driver
@Bean
@ConfigurationProperties(prefix = "maria.datasource")  // 위 설정값 자동 주입
public DataSource mariaDataSource() {
    return DataSourceBuilder.create().build();  // 빈 HikariDataSource 생성
}
// Spring이 setter(setJdbcUrl, setUsername, ...) 호출해서 값을 채워 넣음
실수 포인트 — HikariCP
HikariCP는 url이 아닌 jdbc-url 프로퍼티를 사용. url로 쓰면 "jdbcUrl is required with driverClassName" 에러.

@Primary / @Qualifier — 다중 Bean 충돌 해결

// MySQL (메인 DB) — @Primary로 우선순위 지정
@Primary @Bean
public DataSource dataSource(DataSourceProperties props) {
    return props.initializeDataSourceBuilder().build();
}

// MariaDB — 보조 Bean
@Bean
public DataSource mariaDataSource() {
    return DataSourceBuilder.create().build();
}

// 사용 시 — @Qualifier로 어떤 Bean인지 명시
@Service
public class MariaSqlService {
    public MariaSqlService(@Qualifier("mariaJdbcTemplate") JdbcTemplate jt) {
        this.jdbcTemplate = jt;
    }
}
  • @Primary — 같은 타입 Bean이 여러 개일 때 기본으로 주입될 Bean 지정
  • @Qualifier("이름") — 이름으로 특정 Bean 지목
  • 둘 다 없으면 NoUniqueBeanDefinitionException 발생

@ControllerAdvice / @ModelAttribute — 전역 데이터 주입

@ControllerAdvice   // 모든 @Controller에 공통 적용
public class GlobalModelAdvice {

    @ModelAttribute("ctx")  // 모든 Thymeleaf 뷰에 "ctx" 변수 자동 추가
    public String contextPath(HttpServletRequest request) {
        return request.getContextPath();  // "/v3"
    }
}
<!-- Thymeleaf에서 사용 -->
<a th:href="${ctx} + '/members'">고객 관리</a>

// JS에서 사용
const contextPath = /*[[${ctx}]]*/ '';
왜 필요했냐
context-path가 /v3일 때 fetch('/sql/execute')는 /sql/execute로 가버림.
contextPath를 모든 페이지에서 쓸 수 있도록 @ControllerAdvice로 전역 주입.
Thymeleaf 3.1에서 #request.contextPath가 제거되면서 이 방법으로 해결.

Spring Security 6 핵심

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/login", "/css/**", "/js/**").permitAll()
                .anyRequest().authenticated()
            )
            .formLogin(form -> form.loginPage("/login").defaultSuccessUrl("/"))
            .logout(logout -> logout.logoutSuccessUrl("/login"));
        return http.build();
    }

    @Bean
    public UserDetailsService userDetailsService() {
        UserDetails user = User.withUsername("admin")
            .password(passwordEncoder().encode("admin1234"))
            .roles("ADMIN").build();
        return new InMemoryUserDetailsManager(user);
    }
}

@Transactional 동작 원리

@Service
public class MemberService {

    @Transactional   // AOP 프록시가 감싸서 → BEGIN → 실행 → COMMIT/ROLLBACK
    public void deleteMember(Long id) {
        memberMapper.delete(id);
        subscriptionMapper.deleteByMemberId(id);  // 예외 → 위 delete도 롤백
    }
}
  • RuntimeException(unchecked) → 자동 롤백
  • Checked Exception → 기본 롤백 안 됨 → @Transactional(rollbackFor = Exception.class)
Q. @Transactional이 뭔가요?
"Spring AOP가 메서드를 프록시로 감싸서 트랜잭션을 시작합니다. 메서드가 정상 종료되면 커밋, 예외가 발생하면 롤백해서 데이터 일관성을 보장합니다. RuntimeException은 자동 롤백되고, Checked Exception은 기본적으로 롤백되지 않습니다."

4. MyBatis vs JPA

MyBatisJPA (Hibernate)
SQL직접 작성 (XML 또는 어노테이션)자동 생성 (JPQL 또는 메서드명)
복잡한 쿼리유리 (JOIN, 서브쿼리 직접 제어)불리 (네이티브 쿼리 사용해야 함)
학습 곡선SQL만 알면 됨엔티티/영속성 컨텍스트 개념 필요
유지보수SQL 변경 쉬움모델 변경이 DB에 자동 반영 가능
주요 사용처금융, 레거시, 복잡한 쿼리일반적인 CRUD 위주 시스템

MyBatis XML Mapper 구조

<mapper namespace="com.madayV3.blog.mapper.MemberMapper">

    </update>

    <delete id="delete">
        DELETE FROM member WHERE id=#{id}
    </delete>

    <select id="findPage" resultType="com.madayV3.blog.model.Member">
        SELECT * FROM member
        <where>
            <if test="keyword != null and keyword != ''">
                AND (name LIKE CONCAT('%', #{keyword}, '%')
                  OR email LIKE CONCAT('%', #{keyword}, '%'))
            </if>
        </where>
        ORDER BY created_at DESC
        LIMIT #{limit} OFFSET #{offset}
    </select>

</mapper>
항목설명
#{}PreparedStatement 바인딩 → SQL 인젝션 방지. 사용자 입력에는 반드시 이것
${}문자열 그대로 치환 → SQL 인젝션 위험. 테이블명/컬럼명 동적 변경 시만 사용
useGeneratedKeysAUTO_INCREMENT로 생성된 PK를 Java 객체에 자동 주입
namespace이 XML이 연결되는 @Mapper 인터페이스 전체 경로
<where><if>Dynamic SQL: 조건이 있을 때만 WHERE절 추가
Q. MyBatis를 선택한 이유가 뭔가요?
"JPA는 복잡한 JOIN이나 집계 쿼리를 작성할 때 JPQL이 직관적이지 않고 네이티브 쿼리가 필요한 경우가 많습니다. SQL에 익숙한 환경에서 복잡한 쿼리를 직접 제어하려면 MyBatis가 적합합니다. 특히 금융/레거시 시스템에서 많이 사용됩니다."
Q. #{} 와 ${} 차이가 뭔가요?
"#{} 는 PreparedStatement 파라미터로 바인딩되어 SQL 인젝션을 방지합니다. ${} 는 문자열을 그대로 치환하므로 테이블명/컬럼명처럼 동적으로 변경해야 할 때만 씁니다. 사용자 입력값에는 반드시 #{} 를 써야 합니다."

심화 훅

// useRef — DOM 접근 또는 리렌더링 없이 값 저장
const inputRef = useRef(null);
inputRef.current.focus();      // DOM 접근

const countRef = useRef(0);
countRef.current++;            // 리렌더링 없이 값만 변경

// useReducer — 복잡한 state 로직 (Redux 패턴)
function reducer(state, action) {
    switch (action.type) {
        case 'increment': return { count: state.count + 1 };
        case 'decrement': return { count: state.count - 1 };
        default: return state;
    }
}
const [state, dispatch] = useReducer(reducer, { count: 0 });
dispatch({ type: 'increment' });

// 커스텀 훅 — 반복 로직을 use로 시작하는 함수로 분리
function useFetch(url) {
    const [data, setData] = useState(null);
    const [isLoading, setIsLoading] = useState(true);
    useEffect(() => {
        fetch(url).then(res => res.json()).then(d => { setData(d); setIsLoading(false); });
    }, [url]);
    return { data, isLoading };
}
const { data, isLoading } = useFetch('/api/users');

Q. useState와 일반 변수 차이가 뭔가요?
"일반 변수는 값이 바뀌어도 화면이 리렌더링되지 않습니다. useState는 값이 바뀌면 자동으로 화면을 다시 그려줍니다."
Q. useMemo와 useCallback 차이가 뭔가요?
"useMemo는 계산된 값을 캐싱하고, useCallback은 함수를 캐싱합니다. 둘 다 불필요한 재계산을 막아 성능을 최적화합니다. useMemo는 무거운 계산이 있을 때, useCallback은 자식 컴포넌트에 함수를 전달할 때 사용합니다."
Q. Context API가 뭔가요?
"props를 여러 단계로 전달하지 않고 전역으로 데이터를 공유할 수 있는 기능입니다. props drilling 문제를 해결할 때 씁니다."
Q. Next.js 위주로 했는데 순수 React는요?
"Next.js가 React 기반이라 컴포넌트, 훅, 상태관리는 동일하게 사용했습니다. Next.js는 파일 기반 라우팅과 SSR이 추가된 것이고, 핵심 React 개념은 그대로 사용했습니다."

const [loading, setLoading] = useState(false);
useEffect(() => {
    setLoading(true);
    fetch('/api/users').then(r => r.json()).then(setUsers).finally(() => setLoading(false));
}, []);

// React Query 방식 — 자동으로 처리
const { data: users, isLoading, isError } = useQuery({
    queryKey: ['users'],
    queryFn: () => fetch('/api/users').then(r => r.json()),
    staleTime: 1000 * 60 * 5,   // 5분간 캐시 유지
});
// useMutation — 데이터 변경 (POST/PUT/DELETE)
const queryClient = useQueryClient();
const mutation = useMutation({
    mutationFn: (newUser) => fetch('/api/users', {
        method: 'POST',
        body: JSON.stringify(newUser),
    }),
    onSuccess: () => {
        queryClient.invalidateQueries({ queryKey: ['users'] });  // 캐시 무효화 → 재조회
    },
});
개념설명
queryKey캐시 식별자. 같은 key면 캐시된 데이터 재사용
queryFn실제 데이터를 가져오는 함수
staleTime캐시 유효 시간. 이 시간 안에는 재요청 안 함
invalidateQueries특정 key의 캐시 무효화 → 자동 재조회 트리거
isLoading / isError로딩/에러 상태 자동 제공
Q. React Query를 왜 쓰나요?
"useEffect로 직접 fetch할 때 로딩 상태, 에러 처리, 캐싱을 전부 직접 관리해야 합니다. React Query는 이걸 자동으로 처리해줘서 코드가 간결해지고, 캐싱으로 불필요한 API 호출도 줄어듭니다."
Q. useMutation은 언제 쓰나요?
"데이터를 변경할 때(POST/PUT/DELETE) 씁니다. 성공 후 onSuccess에서 관련 캐시를 무효화해서 화면을 자동으로 최신 상태로 유지할 수 있습니다."

7. DB / SQL Q&A

Q. 트랜잭션이 뭔가요?
"여러 DB 작업을 하나의 묶음으로 처리하는 단위입니다. 전부 성공하거나, 하나라도 실패하면 전부 되돌립니다(rollback)."
예시: 계좌 이체
1. A 계좌에서 -10만원
2. B 계좌에  +10만원
→ 둘 다 성공해야 완료. 중간에 실패하면 둘 다 취소.
Q. ACID가 뭔가요?
"트랜잭션이 안전하게 처리되기 위한 4가지 원칙입니다."
A — Atomicity  (원자성): 전부 성공 or 전부 실패. 중간 없음.
C — Consistency (일관성): 트랜잭션 전후 DB 규칙이 항상 유지됨.
I — Isolation   (격리성): 동시에 실행되는 트랜잭션이 서로 영향 안 줌.
D — Durability  (지속성): 커밋된 데이터는 장애가 나도 사라지지 않음.
Q. JOIN 종류를 설명해보세요.
"두 테이블을 연결해서 데이터를 조회하는 방법입니다."
INNER JOIN → 양쪽에 모두 있는 데이터만
LEFT JOIN  → 왼쪽 테이블 전부 + 오른쪽은 있으면 포함 (없으면 NULL)
RIGHT JOIN → 오른쪽 테이블 전부 + 왼쪽은 있으면 포함 (없으면 NULL)

-- 예시: 주문 안 한 유저도 포함해서 조회
SELECT u.name, o.product
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;
Q. Index가 뭔가요? 왜 쓰나요?
"특정 컬럼을 빠르게 검색하기 위해 만들어두는 색인입니다. 책의 목차처럼 원하는 데이터 위치를 바로 찾아갑니다."
-- 인덱스 없이 → 테이블 전체 스캔 (느림)
-- 인덱스 있으면 → 해당 위치 바로 접근 (빠름)
CREATE INDEX idx_email ON member(email);

단점: INSERT/UPDATE/DELETE 시 인덱스도 갱신해야 해서 쓰기가 약간 느려짐.
→ 조회가 많은 컬럼에만 선별적으로 사용.
Q. WHERE vs HAVING 차이가 뭔가요?
"WHERE는 GROUP BY 이전에 행 단위로 필터링하고, HAVING은 GROUP BY 이후에 그룹 단위로 필터링합니다. WHERE에서는 집계 함수를 쓸 수 없지만 HAVING에서는 사용 가능합니다."
Q. 서브쿼리 IN vs EXISTS 차이가 뭔가요?
"IN은 서브쿼리 결과를 전부 메모리에 올립니다. EXISTS는 일치하는 행 하나만 찾으면 즉시 종료(early termination)합니다. 대용량 데이터에서는 EXISTS가 더 빠릅니다."
Q. 윈도우 함수를 써본 적 있나요?
"있습니다. RANK() OVER (ORDER BY monthly_fee DESC)로 요금제 순위를 구하거나, SUM() OVER ()로 전체 대비 비율을 계산했습니다. GROUP BY가 행을 합치는 반면 윈도우 함수는 원래 행 수를 유지하면서 집계값을 추가해줘서 순위나 비율 계산에 적합합니다."
Q. CTE(WITH 절)를 왜 사용했나요?
"서브쿼리를 중첩하면 가독성이 떨어지고 같은 집계를 여러 번 반복해야 할 때가 있습니다. CTE는 중간 결과에 이름을 붙여서 임시 테이블처럼 참조할 수 있어서 복잡한 쿼리를 단계별로 나눠 쓸 수 있습니다."
Q. MongoDB가 뭔가요? 언제 쓰나요?
"JSON 형태(BSON)로 데이터를 저장하는 NoSQL 데이터베이스입니다. 스키마가 유연해서 문서마다 구조가 달라도 됩니다. 스키마가 자주 바뀌거나 JSON 데이터를 그대로 저장할 때, 실시간 로그/채팅/콘텐츠 관리에 씁니다."
Q. DynamoDB가 뭔가요?
"AWS에서 제공하는 완전관리형 NoSQL 데이터베이스입니다. 서버리스로 운영되고 자동 스케일링됩니다. Partition Key로 데이터를 분산 저장하고, 매우 빠른 읽기/쓰기(한 자릿수 ms)가 특징입니다. AWS Lambda와 잘 맞는 서버리스 프로젝트에 씁니다."
Q. SQL vs NoSQL 언제 뭘 쓰나요?
"데이터 정합성이 중요하고 복잡한 관계가 있으면 SQL(RDB). 대용량, 빠른 읽기쓰기, 유연한 스키마가 필요하면 NoSQL. 예를 들어 은행 시스템은 SQL, SNS 피드나 로그는 NoSQL이 적합합니다."

8. 프로젝트 기반 예상 Q&A

Q. 프로젝트에서 MariaDB를 어떻게 사용했나요?
"Spring Boot에서 MySQL(메인 DB)과 MariaDB(SQL 연습용)를 멀티 데이터소스로 구성했습니다. @Primary로 MySQL을 기본 DataSource로 지정하고, MariaDB는 @Qualifier("mariaJdbcTemplate")로 명시해서 JdbcTemplate을 별도 주입했습니다. application.properties에서 maria.datasource.jdbc-url로 분리 관리했습니다."
Q. @ConfigurationProperties를 왜 사용했나요?
"application.properties의 설정값을 @Value로 하나씩 넣는 대신, @ConfigurationProperties(prefix = "maria.datasource")로 DataSource 객체에 한 번에 바인딩했습니다. 설정 변경 시 properties 파일만 수정하면 되어서 유지보수가 쉽습니다."
Q. context-path를 왜 설정했나요?
"한 서버에서 v2, v3 두 버전의 앱을 동시에 서비스하기 위해서입니다. server.servlet.context-path=/v3으로 설정하고 Nginx에서 /v3/ 경로는 8082 포트(v3)로, /v2/는 8081 포트(v2)로 프록시했습니다. 도메인 하나로 여러 앱을 운영하는 방식입니다."
Q. MyBatis를 선택한 이유가 뭔가요?
"JPA는 복잡한 JOIN이나 집계 쿼리를 작성할 때 JPQL이 직관적이지 않습니다. SQL에 익숙한 환경에서 복잡한 쿼리를 직접 제어하려면 MyBatis가 적합합니다. 특히 금융/레거시 시스템에서 많이 사용됩니다."
Q. CI/CD 어떻게 구성했나요?
"GitHub Actions를 사용했습니다. main 브랜치에 push하면 appleboy/ssh-action으로 OCI 서버에 SSH 접속해서 git pull → mvn package → docker-compose up --build 순서로 자동 배포됩니다. OCI ARM 아키텍처라서 GitHub Actions에서 직접 빌드하지 않고 서버에서 빌드하는 방식을 택했습니다."
Q. @Transactional을 사용한 경우가 있나요?
"고객 삭제 시 subscription 테이블 관련 데이터도 함께 삭제해야 하는 경우에 사용했습니다. 하나의 메서드 안에서 member 삭제와 subscription 삭제가 모두 성공해야 하고, 하나라도 실패하면 전체 롤백되어야 하기 때문입니다."
Q. Spring Security에서 CSRF가 뭔가요?
"Cross-Site Request Forgery. 악의적인 사이트가 로그인된 사용자의 권한으로 요청을 위조하는 공격입니다. Spring Security는 기본으로 CSRF 토큰을 발급하고, POST/PUT/DELETE 요청 시 토큰이 없으면 거부합니다. Ajax에서는 메타 태그에 담은 _csrf 토큰을 헤더에 담아서 전송합니다."
Q. Docker를 왜 사용했나요?
"환경 일관성 때문입니다. 로컬 개발 환경과 운영 서버(OCI)의 Java 버전, DB 버전 차이로 인한 문제를 없앨 수 있습니다. docker-compose로 MySQL, MariaDB, 앱 서버를 한 번에 올리고 내릴 수 있어서 관리가 편합니다."
Q. 프로젝트하면서 가장 어려웠던 버그가 뭔가요?
"멀티 데이터소스 구성 시 HikariCP의 jdbc-url 문제였습니다. @ConfigurationProperties로 MariaDB DataSource를 만들 때 프로퍼티를 url로 설정했더니 'jdbcUrl is required with driverClassName' 에러가 발생했습니다. HikariCP는 내부적으로 url 대신 jdbc-url 프로퍼티를 사용하기 때문이었습니다. @Primary JdbcTemplate을 추가해서 JdbcTemplateAutoConfiguration이 올바른 DataSource를 사용하도록 하는 과정도 디버깅이 필요했습니다."
Q. RESTful API가 뭔가요?
"HTTP 메서드(GET/POST/PUT/DELETE)와 URL로 자원을 표현하는 API 설계 방식입니다. 무상태(Stateless)로 동작해서 확장성이 좋습니다."
GET    /api/members        → 전체 목록
GET    /api/members/{id}   → 단건 조회
POST   /api/members        → 생성
PUT    /api/members/{id}   → 수정
DELETE /api/members/{id}   → 삭제
Q. 프로젝트에서 가장 신경 쓴 부분이 뭔가요?
"V3에서 MySQL과 MariaDB를 멀티 데이터소스로 구성하고, Thymeleaf + Ajax REST API를 함께 사용하면서 발생하는 여러 버그들을 직접 해결하는 과정이었습니다. 특히 @Primary/@Qualifier 설정, HikariCP jdbc-url 문제, Thymeleaf 3.1 보안 강화로 인한 th:onclick 제거 이슈를 하나씩 해결하면서 Spring 내부 동작 원리에 대한 이해가 깊어졌습니다."
